# VTGUI · DRMLAB / unshackle 独立任务工作台

独立 Windows 桌面程序。无需放入 DRMLAB 目录，不导入其 Python 模块，也不修改其源码、配置或历史文件。首次启动后选择 DRMLAB 或 unshackle 所在目录，即可在该目录运行命令。

## 启动

**安装包（推荐分享）**：将 `dist/VTGUI-1.8.0-Setup-x64.exe` 发送给其他人即可。双击后按中文向导安装，支持选择安装位置、开始菜单入口及可选桌面快捷方式。适用于 Windows 10/11 x64，离线安装，无需安装 Python，也无需管理员权限。安装后从开始菜单启动 VTGUI，选择接收方自己的 DRMLAB 目录。

安装包只含 GUI 和运行库，不含分享者的配置、日志、定时任务或 DRMLAB。DRMLAB 及其依赖仍需自行准备。升级前先正常退出 GUI，运行新安装包即可覆盖安装；从 Windows“已安装的应用”或开始菜单卸载，均保留 `%LOCALAPPDATA%\VTGUI` 中的配置和日志，不删除 DRMLAB 及下载文件。安装包未进行数字签名。

**免安装文件夹版**：双击 `dist/VTGUI/VTGUI.exe`。分发此版本时需要复制整个 `dist/VTGUI` 文件夹，不能只复制 exe。

**源码版本**：安装包含 Tk 的 Python 3.11 或以上版本，双击 `RUN.bat`，或执行：

```powershell
python main.py
```

GUI 的源码运行仅依赖 Python 标准库。DRMLAB 自己所需的 Poetry、虚拟环境和相关二进制工具仍需安装好。可以在“工作区设置 → 检查运行环境”查看路径查找结果。

`RUN.bat` 使用无控制台的 Python 启动 GUI，启动终端会自动退出，不会一直占用窗口。依次查找项目 `.venv` 的 `pythonw.exe`、系统 `pyw.exe`、`pythonw.exe`；没有 Python 时尝试已打包的 EXE。GUI 启动异常仍会弹窗提示，并写入数据目录的 `startup-error.log`。

## unshackle 支持

选择项目根目录 `E:\unshackle-dev`，然后输入原本使用的命令，例如 `uv run unshackle dl ...` 或 `unshackle dl ...`。VTGUI 自动识别目录中的 `unshackle` 包，并在环境检查中显示 `uv`、`unshackle` 及其他工具的查找结果。命令在对应项目根目录运行，优先使用该项目的 `.venv/Scripts` 和 `binaries`。

本地 unshackle 与 DRMLAB 使用相同的完成路径标记：

```text
===VT_FINAL_DIR=== E:\unshackle-dev\downloads\Example.Series
===VT_FINAL_FILE=== E:\unshackle-dev\downloads\Example.Series\Episode.mkv
```

终端保留原始输出。定时任务成功后，若输出包含这些标记，仅从标记关联的路径中选取本次新增/更新成品，再执行稳定性检查、重命名和移动。兼容分段输出、ANSI 颜色、中文及空格路径。未输出标记的命令继续使用原有目录快照方式。标记不会扩大任务配置的成品目录或通配符范围，也不会触发单次任务的自动移动；失败、取消的任务不会处理成品。

定时任务的执行目录设为 unshackle 根目录；成品目录默认 `downloads`，如果 unshackle 配置或命令的 `--output-dir` 指向其他位置，请同步修改任务的成品目录。目的地、移动方式、重命名和逐集配置方式与 DRMLAB 相同。不同项目的定时任务各自保存执行目录，可在同一队列中执行。

“监听 DRMLAB 历史记录”只适用于 DRMLAB 原 GUI，不用于 unshackle。unshackle 下载任务直接在本工作台或定时任务中执行即可。GUI 不修改两项目的源码或配置；已有 DRMLAB 任务和设置继续有效。

## 多工作目录与编辑页进度

支持保存至多 3 个工作目录。在“工作区设置”的三行目录中添加或修改，清空某行并保存即可移除；顶部“添加目录”也可快速添加。旧版本的单目录配置自动作为第一个目录保留。重复目录会合并，第四个目录会提示先移除一个。

单次任务在顶部工作目录下拉框中选择，定时任务在编辑页“工作目录”下拉框中选择。每个任务和队列记录独立保存执行目录；切换默认目录、切换单次任务目录或从列表移除目录，不会改写已有任务。默认目录用于新建定时任务及原 GUI 历史监听。

逐集定时任务编辑页的“起始 Episode”显示当前下一待执行集，并在编辑页保持打开时随成功进度更新；原有补零格式保留。失败、取消及重试期间保持待完成集数。直接保存或修改时间等其他设置会保留进度；手动改动起始集数才会重设起点，正在执行的轮次仍禁止重设。

全部集数完成后，起始框显示末集之后的下一编号，并标注“全部完成”；仍可直接保存，增加末集编号后会从下一集继续，不会重跑已完成集数。

## 功能

### 命令工作台

1. 点击顶部“添加目录”，添加工作目录（至多 3 个），再在下拉框中选定本次任务的目录，例如 `E:\DRMLAB` 或 `E:\unshackle-dev`。
2. 输入任务名称和原本在终端中使用的命令，选择 CMD 或 PowerShell。
3. 点击“执行任务”或按 `Ctrl + Enter`。
4. 左侧显示等待、执行、完成、失败、取消和中断记录，点击记录切换日志，双击查看完整任务配置。

支持多行命令、实时标准输出及错误输出、普通文本交互输入、日志查找、清屏和完整日志导出。按 `Ctrl + F` 聚焦查找框。

命令的工作目录始终是对应任务保存的所选工作目录。环境变量会继承 GUI 的启动环境，并优先加入 `<DRMLAB>/.venv/Scripts` 和 `<DRMLAB>/binaries`。每个任务有独立的终端进程，上一任务中的 `cd`、`set` 不影响下一任务；需要设置环境时请写在同一个任务内。

这是进程输出工作台，不是完整的伪终端：不支持需要完整 TTY 的全屏界面、光标绘制、密码隐藏输入等。输出编码默认 UTF-8；旧工具乱码可在设置或定时任务中改为 `gb18030`。

可先用无副作用的命令测试：

```bat
echo VTGUI test
cd
```

### 定时任务

在“定时任务”中创建任务，设置 `HH:MM`，勾选周一至周日中任意一天或多天。“每天”选择全部七天，“工作日”选择周一到周五。可编辑、暂停、启用、删除或立即执行。

点击“+ 添加时间”可在原执行时间之外额外添加至多 **3 个时间**（每天合计最多 4 个），点击“移除”可删除额外时间。所有时间共用所选星期，例如只勾选周一，设置 `09:00`、`12:00`、`18:00`、`23:00`，每周一会分别触发四次。时间不可重复，新增时间必须填写有效的 `HH:MM`；旧任务继续使用原执行时间。任务列表展示全部时间，“下次执行”显示最近的一个时间点。

- 使用**电脑本地时区**，24 小时制；修改系统时区会影响调度。
- 每个定时任务独立保存执行目录、命令、编码、超时及结果处理规则。切换全局目录不会改变已有定时任务，可在编辑器中更新。
- 到点后进入串行队列，同一时刻最多运行一个任务，避免本工具的多个下载争用成品文件。
- 同一任务在同一分钟内只触发一次，去重信息持久化。
- **程序必须保持运行**，最小化后继续执行。关闭、关机或休眠期间错过的计划不补跑，不会自动唤醒电脑。
- 等待队列会保留，重新打开 GUI 后继续执行。上次运行中意外中断的任务会标为“已中断”，需核实后手动重试。

### 使用 `{episode}` 按集数执行

在定时任务命令中写入 `{episode}`，并在编辑器的“逐集执行”中配置：

- **起始 Episode**：首次执行的集编号。例如填 `01`，占位符依次替换为 `01`、`02`……；填 `1` 则不补零。支持在同一命令中多次使用，其他花括号内容不受影响。
- **总集数 / 末集编号**：最后一集的编号。例如起始 `05`、总集数 `24`，执行范围为第 5～24 集。
- **每次触发集数**：每轮最多依次执行多少集。最后一轮只执行剩余集数，不会超过末集编号。

例如命令 `your-command -w S01E{episode}`，起始 `01`、总集数 `12`、每次触发 `2`：第一轮成功执行 `S01E01` 后才创建 `S01E02` 任务；下一轮从 `S01E03` 继续。每集都有独立的记录和日志，名称中会标注 Episode。

**完成才续跑**：同一轮始终只安排当前一集。当前集失败时先按规则限次重试，重试成功才安排下一集；重试耗尽、手动取消或意外中断时停止本轮，不跳过失败集。下次定时触发或点击该定时任务的“立即执行”，从尚未完成的集继续，每轮重新计算集数上限。逐集记录的“重试”按钮会提示使用定时任务的“立即执行”，避免绕开进度管理。

进度、轮次和待执行集持久化保存。正常退出时保留的等待任务会在下次打开后执行；意外中断的当前集不会自动跳过，需等下一次触发或手动“立即执行”。同一计划上一轮尚在执行或等待重试时，新触发会跳过，避免同时下载同一集。所有集完成后停止触发，列表显示“全部完成”。

修改时间、命令或处理规则不会重置进度，正在运行的一轮使用触发时保存的配置；编辑页起始 Episode 随已完成进度显示下一待执行集；手动修改该值才会重置到新起点。为避免冲突，当前轮次结束或取消之前不能修改三项集数配置或移除占位符。暂停定时计划只影响后续定时触发；若要停止当前轮次，请在工作台取消当前集。删除定时计划会停止后续集数，已在运行的当前集继续执行。

不含 `{episode}` 的定时任务继续按普通任务运行，逐集配置不生效。每集应用该定时任务自己的移动规则；目标已有同名剧集目录时递归合并，新增集数与字幕继续移入，同名文件跳过。

### 定时任务重命名规则

在定时任务编辑器中展开“重命名规则 · 成功后、移动前”，可配置以下三项，留空的项目跳过：

| 顺序 | 规则 | 填写示例 | 效果 |
| --- | --- | --- | --- |
| 1 | 季号 SXX | `S02` 或 `02` | 将名称中的季号指定为 S02 |
| 1 | 季号偏移 | `+1` / `-1` | S01 → S02 / S02 → S01 |
| 2 | 集号 EXX | `E12` 或 `12` | 将名称中的集号指定为 E12 |
| 2 | 集号偏移 | `+2` / `-2` | E01 → E03 / E03 → E01 |
| 3 | 替换词 | `Xiong.Mei => Brother.Sister` | 按字面字符串替换，区分大小写 |

同时配置时，严格按 **季号 → 集号 → 字符串替换** 计算最终名称；多行替换词从上到下依次处理。替换词右侧可留空以删除原词。季号和集号保留原有位数，至少补齐两位；原有小写 s/e 保持大小写。

例如季号 `+1`、集号 `-1`、替换词 `Xiong.Mei => Brother.Sister`：

```text
剧集目录：Xiong.Mei.S01        → Brother.Sister.S02
视频文件：Xiong.Mei.S01E03.mkv → Brother.Sister.S02E02.mkv
字幕文件：Xiong.Mei.S01E03.srt → Brother.Sister.S02E02.srt
```

可用“名称预览”输入测试文件名，不会修改磁盘文件。文件只处理名称主体，保留最后一个扩展名；文件夹按整个目录名处理。处理范围是本次任务完成的文件所关联的一级剧集目录，包括目录里的已有集数、字幕、封面和所有子目录；成品目录下的散文件也支持处理。无关、未被本次任务关联的剧集不处理。即使选择“仅成品文件”移动，重命名仍会处理关联的剧集目录及其全部文件，但只移动本次选中的成品。

处理顺序是：**下载成功 → 稳定性检查 → 名称预检 → 完成重命名 → 按任务配置移动或合并**。关闭自动移动也可以只重命名；成品目录和通配符仍需配置。编号结果不能小于 0，名称不能包含 Windows 非法字符或保留名称；多个源文件重命名后同名、重命名目标存在文件/目录类型冲突或链接，或移动目标同名剧集项目不是普通目录时，停止后处理。重命名后的目录已存在时递归合并，同名普通文件由本次文件覆盖，已有的其他集数和文件保留。目标已有普通剧集目录可以合并，已有同名文件不影响其他新增文件移动。

重命名采用临时名称过渡，支持 E01→E02、E02→E03 这样的顺序偏移，也支持仅大小写变更。覆盖前暂存已有文件，全部重命名及校验成功后清理备份。中途出错或取消时，会尝试倒序恢复原名和被覆盖文件；恢复失败时保留记录供核对，不执行移动。**重命名失败不会重新运行下载命令，也不会继续下一集**，需要检查记录后再从定时任务页手动触发。移动结束后，同名跳过或移动失败而留在源目录的项目会恢复原始名称，已移动文件保持新名称；重命名时合并的已有目录及原有其他文件保持名称。这能避免下一集下载与源目录里已改名的剩余文件发生冲突。恢复过程也会留下单独记录，失败时不会覆盖源文件。

每次实际重命名会保存 `logs/<任务ID>.rename.json`，包含路径映射、操作顺序、完成状态及文件标识。同一组规则下，仍留在源目录且标识未变的已处理文件和目录，不会再次叠加偏移；新文件继续按规则处理。不要清理这些记录后反复对同一批源文件应用相对偏移。

若程序在重命名期间被强制关闭，或恢复原名失败，后续重命名会阻止操作并指出对应记录。先按记录核实并恢复名称，再将该记录移出 logs 备份后重新执行，避免猜测路径造成覆盖。

### 失败和完成钩子

“工作区设置”只提供默认失败重试和超时设置。**移动只在“定时任务 → 新建/编辑 → 结果处理”中配置**：每个任务独立选择是否开启、成品目录、目的地、移动方式及通配符。新任务默认关闭移动；单次任务及外部历史监听不继承移动配置。

升级到 1.4.0 后，旧全局移动配置会移除，定时任务中已经保存的配置保留；旧等待队列里非定时任务继承的移动/重命名会关闭。定时任务和其重试仍保留本任务的处理规则。

- **失败重试**：非零退出码、启动异常或超时视为失败。配置移动或重命名的任务即使退出码为 `0`，若没有可确认的新增/更新成品，也按失败处理，原因显示“当前集未更新”；逐集进度保持当前集，并按配置重试。支持 0–20 次重试及 1–86400 秒间隔，每次尝试独立保留日志。`0` 表示关闭自动重试。
- **超时**：设为 `0` 不限制；否则超时后终止任务进程树，按失败处理。
- **手动取消**：终止任务进程树，不触发自动重试。
- **成功移动**：定时任务开启移动后，仅在退出码为 `0`、重命名（如配置）成功后进行。“剧集文件夹”模式会处理本次有新增或更新成品的一级剧集目录及其中的集数、字幕、封面和子目录；无关目录保持原位，根目录散文件单独移动。
- **移动范围**：成品目录应设为各剧集文件夹的上级，例如 `downloads`；`downloads/剧集A/` 会完整移动至 `<目标>/剧集A/`。若有多季子目录，也会随剧集文件夹一起移动。通配符用于识别完成的媒体文件，不会过滤同一剧集目录内的字幕或封面。
- **仅成品文件**：仅移动本次新增的匹配成品，按文件名直接放进所选目标目录，不再附加源剧集目录或其他子目录；源文件夹和未选中的文件保留。例如目标已选为 `D:\同步剧\Light.the.Dark.S01...`，成品直接放入该目录，不会再嵌套一层同名剧集文件夹。同名文件跳过、不覆盖，源文件保留。此行为在 1.4.1 修正，已有定时任务无需修改配置。
- **目录合并**：目标已有同名普通剧集目录时递归合并，包括已有的季目录和字幕子目录，不再整部跳过。只把目标尚未存在的文件移入，同名文件无论内容是否相同都跳过、不覆盖、不删除源文件；文件/目录类型冲突只跳过对应项目，其他文件继续处理。只移除已搬空的源目录，含重复项或失败项的源目录保留。日志显示移入数量和跳过原因。
- **目录稳定检查**：整部剧集的文件、子目录必须保持稳定；有 `.part`、`.partial`、`.tmp`、`.temp`、`.download`、`.downloading`、`.crdownload`、`.aria2` 临时项、空的媒体文件或链接时，整部跳过并记录原因。
- **跨盘移动**：新剧集目录先完整暂存和校验，再发布目标目录；已有剧集目录按文件暂存、校验和发布，完成一个再移除对应源文件。取消或单文件失败时保留尚未移动的源文件，已经移动到目标的文件保留。目标链接/重解析目录不会被跟随。

成品目录和目标目录不能相同或互相包含。相对路径以任务的 DRMLAB 根目录为基准。默认通配符为 `*.mkv;*.mp4;*.mka;*.mks`，可根据实际输出修改。

本工具串行运行自己的任务；快照无法证明其他程序所写文件的归属，因此启用自动移动时，请让该成品目录仅供这些任务使用。无需等到整部剧完结才触发，可以每次将新增集数合并到同一个目的地。已经运行的 GUI 需重启后加载新版代码。

### Telegram Bot 通知

在“工作区设置 → Telegram Bot 通知”填写 **Bot Token** 和 **接收聊天 ID**，点击“保存设置”后启用。多个聊天 ID 用逗号分隔，例如 `123456789,-1001234567890`；支持负数群组 ID 和 `@频道用户名`，空白及重复项会自动整理。两项均清空并保存可关闭通知。配置即时应用于后续产生的通知，已有定时任务无需重新保存。

- Token 由 Telegram 的 BotFather 创建 Bot 时提供。私聊接收者需先向 Bot 发送 `/start`，群组或频道需加入 Bot 并授予发送权限。
- “发送测试通知”使用当前输入内容，向所有填写的接收方发送测试消息，无需先保存。到“结果与钩子”查看逐个接收方的发送结果。
- 通知本工具任务的完成、失败和取消（含等待队列手动取消），以及历史监听捕获的新增完成/失败结果。重命名、移动等后处理结束后才通知任务结果；每次重试、每集分别通知，失败通知不代表后续不会重试。
- 本工具的任务通知包含任务名、来源、尝试次数、结束时间、结果摘要及任务 ID；不附加完整命令或日志。历史监听首次建立基线时不通知，已处理的历史结果不会重复通知。
- 按 [Telegram Bot API 的 sendMessage 接口](https://core.telegram.org/bots/api#sendmessage) 通过 HTTPS 发送纯文本。长消息截断至接口限制以内；网络发送在独立后台队列进行，单个接收方失败后继续处理其他接收方，不影响任务状态、重试、移动或逐集续跑。
- 发送失败只记录事件，不自动补发。待发通知仅保存在内存中，关闭程序会停止发送，重启不会补发；请在退出前查看发送结果。电脑需能连接 Telegram，可使用系统代理或 `HTTPS_PROXY` 环境变量。

Token 输入框默认隐藏，可点击“显示”查看。Token **以明文保存在本机 `vtgui.db` 配置中**，不会复制到定时任务或执行记录；请妥善保管配置备份。

### 监听原 GUI 的执行记录

参考目录中原 GUI 的实际实现：

- `core/download_manager.py` 按退出码报告 `completed` 或 `failed`。
- `core/history_manager.py` 写入 JSON 数组。
- 默认文件是 `<DRMLAB>/vinetrimmer/download_history.json`。
- 原实现没有进程外可直接订阅的 HTTP/事件钩子。

本项目以只读轮询适配该文件，不依赖原 GUI 进程或其模块。在“结果与钩子”中开启监听。路径可在设置中修改。

- 每 2 秒检查一次。首次开启或切换历史文件后，以已有记录建立基线，只处理后续新增的完成/失败记录。
- 去重信息保存于本工具数据库，重启不会再次处理已看到的记录。
- 文件暂不存在、正在写入或 JSON 不完整时会报告状态，并在后续继续检查。
- 外部失败记录若带 `argv` 或 `command`，直接使用对应命令；否则按参考 GUI 支持的 `service`、`url` 和 `params` 还原为 `poetry run vt dl ...` 的独立参数列表。存在无法还原的非空参数时会跳过并提示手动处理。
- 外部原始失败算作第 0 次尝试，之后的总重试次数受规则上限约束。
- 外部完成记录只产生结果事件，不自动移动；即使包含 `files` / `file_path` 或 `folders` / `folder_path` 也不会继承任何目的地。需要自动移动时，请由配置了移动规则的定时任务执行对应命令。

历史文件示例（JSON 数组；路径字段不参与自动移动）：

```json
[
  {
    "id": "unique-task-001",
    "timestamp": "2026-10-18T09:30:00+08:00",
    "status": "completed",
    "folders": ["downloads/Example.Series"]
  },
  {
    "id": "unique-task-002",
    "timestamp": "2026-10-18T09:35:00+08:00",
    "status": "failed",
    "command": "your-original-command"
  }
]
```

本工具不会向原 GUI 的历史文件写入自己的任务。自己的全部执行记录与钩子操作单独保存。

## 数据和日志

默认位于 `%LOCALAPPDATA%\VTGUI`：

```text
vtgui.db           SQLite 配置、定时任务、执行记录、事件与去重信息
logs/<任务ID>.log   UTF-8 完整终端日志
logs/<任务ID>.cmd   CMD 模式的任务脚本
logs/<任务ID>.rename.json  重命名路径、步骤、状态和文件标识（启用重命名时生成）
logs/<任务ID>.unmoved.rename.json  未移动项目恢复原名的记录（如需恢复时生成）
instance.lock      防止同一数据目录启动多个调度器的进程锁
startup-error.log  仅启动异常时生成
```

日志和任务脚本会包含你输入的命令及命令输出。可点击侧栏“打开数据目录”查看、备份。请退出程序后备份数据库及相关 WAL 文件。终端只显示末尾约 1MB，完整内容可导出。数据和日志不会自动清理。

需要便携存储或测试隔离时：

```powershell
python main.py --data-dir E:\VTGUI-Data
```

同一个数据目录仅允许一个实例。更换数据目录会使用一套独立的任务和调度。

## 开发、测试与打包

### GitHub Actions 自动打包与 GHCR 归档

推送到 `main`、提交面向 `main` 的 Pull Request，或在 Actions 中手动运行 **Windows packages and GHCR archive**，会在 Windows x64 上执行源码/UI 测试、构建程序与离线安装包、验证打包程序，以及验证安装、升级和卸载。全部通过后，Actions 的 Artifacts 提供安装包、便携 ZIP、构建信息与 SHA-256 校验文件，保留 30 天。

`main` 和 `v*` 标签的成功构建另外使用 [ORAS](https://oras.land/docs/) 将同一批 Windows 文件上传至 GHCR，并重新拉取、校验全部文件后发布别名。归档地址为 `ghcr.io/<GitHub用户名>/<小写仓库名>`；`latest` 对应最新成功的 `main` 构建，`sha-<完整提交哈希>` 对应提交，`build-<运行ID>-<重跑次数>` 对应单次构建。版本标签还会产生 `v1.8.0`、`1.8.0` 这样的归档标签，以及附带下载文件的 GitHub Release。标签必须与 `pyproject.toml` 中的版本一致。

GHCR 中保存的是 Windows 文件的 OCI 归档，使用 ORAS 取回后在 Windows 运行。仓库保持私有；新 GHCR 包默认私有，并通过来源标注关联仓库。流水线使用自动提供的 `GITHUB_TOKEN`，无需另配上传密钥。私有归档的本机下载需要有包读取权限的 GitHub 登录及 `read:packages` 令牌：

```powershell
# 先设置 GHCR_TOKEN 环境变量；不要将令牌写入源码或提交到 Git。
$env:GHCR_TOKEN | oras login ghcr.io --username <GitHub用户名> --password-stdin
oras pull ghcr.io/<GitHub用户名>/<小写仓库名>:latest --output .\VTGUI-download
```

发布新版时，先修改 `pyproject.toml` 中的三段数字版本并提交，再推送匹配标签，例如：

```powershell
git tag v1.8.0
git push origin v1.8.0
```

每次构建的 Actions 摘要会列出实际 GHCR 引用和已校验的 digest。可使用 `@sha256:...` 引用取回该次构建的确定版本。便携 ZIP 解压后运行 `VTGUI/VTGUI.exe`，保留整个文件夹。

### 本地构建

```powershell
# 自动化测试：全部使用临时目录和模拟进程，不执行真实 DRMLAB 下载
python -m unittest discover -s tests -v

# 界面启动检查，不启动调度引擎
python main.py --smoke-test --data-dir .qa\smoke

# 验证已打包 EXE（额外包含一次完整的外部命令/重试/移动测试）
$env:VTGUI_TEST_EXE = "$PWD\dist\VTGUI\VTGUI.exe"
python -m unittest discover -s tests -v

# 生成无需 Python 的 Windows 文件夹版
powershell -ExecutionPolicy Bypass -File .\build.ps1

# 重新构建程序并生成单文件离线安装包
powershell -ExecutionPolicy Bypass -File .\build-installer.ps1

# 已构建最新程序时，只重新生成安装包
powershell -ExecutionPolicy Bypass -File .\build-installer.ps1 -SkipAppBuild
```

`build.ps1` 只在打包时安装 PyInstaller。输出目录为 `dist/VTGUI`，包含 `VTGUI.exe` 及其运行库。项目组织：`vtgui/core.py` 为持久化、执行引擎和结果适配；`vtgui/ui.py` 为中文桌面界面；`main.py` 为入口；`tests/` 为引擎和界面集成验证。

`build-installer.ps1` 默认先调用 `build.ps1`，再使用 [NSIS](https://nsis.sourceforge.io/Download) 生成 `dist/VTGUI-<版本>-Setup-x64.exe` 和 `.exe.sha256` 校验文件。首次构建会从官方 SourceForge 下载 NSIS 3.12 到 `.tools/`，校验官方公布的 SHA-256 后解压；不会安装系统级构建工具。以后使用本地缓存，也可通过 `-MakeNSIS C:\path\makensis.exe` 指定已有编译器。接收方安装和运行 GUI 均不需要联网下载 Python 或 NSIS。
